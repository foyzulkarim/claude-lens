# Task 118: bug: wide-range /api/metrics queries pin the event loop for 15–90s

- **Type:** fix
- **Source:** GitHub issue #118
- **State:** OPEN
- **Labels:** none
- **Created:** 2026-07-24

## Description


Found while diagnosing the reported "navigating between pages shows stale data for 15–30 seconds" against the live npx deployment (2026-07-24). Ingest and most endpoints are fast (full 130MB corpus cold-ingests in 0.29s per the #P5-1 log; `/api/sessions` answers in 15ms) — the stall is entirely in series-mode metrics queries over wide date ranges.

## Symptom

Any series-mode `/api/metrics` query with a wide range takes tens of seconds of **synchronous** compute. Because the engine runs on the event loop, every other request queues behind it, so all mounted `ChartCard`s (which use `placeholderData: keepPreviousData`) show stale data until the pathological query finishes — the user-visible 15–30s freeze on page navigation.

## Repro

Against a live server over a real corpus (130MB, 357 files, 128 sessions / 5,541 calls):

```bash
# 28.8s
curl -X POST -H 'content-type: application/json' http://localhost:4128/api/metrics -d '{"measures":["costComputed","apiCalls","sessions"],"dimensions":["time","project"],"grain":"day","range":{"from":"2025-01-01T00:00:00.000Z","to":"2026-07-24T23:59:59.999Z"},"compare":"previous-period","smoothing":"ma7"}'

# 91.5s (server log responseTime: 91502)
curl -X POST -H 'content-type: application/json' http://localhost:4128/api/metrics -d '{"measures":["costComputed"],"dimensions":["time","model"],"grain":"hour","range":{"from":"2025-01-01T00:00:00.000Z","to":"2026-07-24T23:59:59.999Z"}}'
```

Head-of-line blocking confirmed: a ~2.2s `gatePassRate` query issued during the 91.5s query measured **31.8s** wall clock (~29s of it queued). Same corpus, call-level distribution over the same all-time range: **0.024s** — the cost is specific to the series bucket loop, not data volume.

## Expected vs actual

- Expected: any preset query over the full corpus answers well inside the #P5-1 100ms query target; one slow query never freezes the rest of the app.
- Actual: 28–91s for wide-range series queries; all concurrent requests stall behind them.

## Suspected area

`server/metrics/engine.ts` — `computeSeriesForRange` calls `scopeFor` once per **measure × group × bucket** (triple loop at `engine.ts:317–329`), and `scopeFor` (`engine.ts:241`) re-filters `group.calls`, **all** turns, and **all** sessions per bucket, re-running `Date.parse` on the same timestamp strings each time. All-time at hour grain ≈ 13,600 buckets × groups × measures → O(measures × groups × buckets × (calls + turns + sessions)) with repeated string date parsing. `compare: "previous-period"` doubles it.

Fix shape (for the architecture pass to confirm): invert to one pass over records — compute `bucketStart(epochMs)` once per record and accumulate into per-(group, bucket) scopes; store pre-parsed epoch-ms timestamps in the columnar store at ingest instead of `Date.parse` at query time. Follow-up hardening options: result cache keyed by (query, store version) and/or moving the engine off the event loop.

The #P5-1 benchmark passed because it never exercised these shapes — the fix should extend `server/ingest/benchmark.ts` with wide-range/hour-grain/breakdown query cases so this regresses loudly, and record a new row in the plan's benchmark log.
