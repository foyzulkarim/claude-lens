# Task 119: feat: per-query instrumentation for /api/metrics (slow-query logs, Server-Timing, event-loop lag)

- **Type:** feat
- **Source:** GitHub issue #119
- **State:** OPEN
- **Labels:** none
- **Created:** 2026-07-24

## Description


Follow-up to the 2026-07-24 perf investigation (see the wide-range metrics bug draft): Fastify's `responseTime` log proved a request took 91.5s but said nothing about *which query shape* or *where the time went*, and could not distinguish "this request was slow" from "this request was queued behind a slow one". Instrumentation turns future "the app feels slow" reports into log data that names the culprit directly.

## What & why

Three additions, all server-side, no product behavior change:

1. **Structured per-query log line on `/api/metrics`**: query shape (measures, dimensions, grain, range span in days, mode, compare/smoothing) plus a timing breakdown — `filterGroupMs`, `groupCount`, `bucketCount`, `computeMs`, total. Emit at `info`; escalate to `warn` above a slow-query threshold (~250ms). A `bucketCount: 13608` in a warn line would have identified the current bug on day one.
2. **`Server-Timing` response header** on `/api/metrics` (e.g. `engine;dur=…`) so the same breakdown is visible per chart in the browser DevTools Network tab without server log access.
3. **Event-loop lag monitor** via `perf_hooks.monitorEventLoopDelay`, logging a `warn` when p99 lag exceeds a threshold (~200ms) — the direct signal for "one synchronous query starved every other request".

## Acceptance

- every `/api/metrics` request logs one structured line with query shape and the timing breakdown above; requests over the slow threshold log at `warn`
- `/api/metrics` responses carry a `Server-Timing` header with the engine duration
- sustained event-loop delay (p99 over threshold) produces a `warn` log with the measured lag
- thresholds are constants in one place (config plumbing not required for MVP)
- unit coverage for the log-shape and header (threshold behavior pinned)

## Dependencies
- Depends on: none — independent of the engine fix, but landing it first (or together) lets the fix be verified from the logs
- Unblocks: none
